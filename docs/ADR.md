## 1. 백엔드 패키지 구조: 계층 × feature-first

- **Status**: Accepted (2026-08-21) · **관련 커밋**: `3e71aa6`(초기 스캐폴딩), `acbb7b9`(현재 구조로 재편)

**배경.** 초기 스캐폴딩은 `presentation`/`application`을 별도 최상위 계층으로 뒀다.
하루 만에 다시 갈아엎었다 — 계층을 세분화할수록 기능 하나를 수정할 때 건드려야 하는
디렉터리가 늘어나고, 프로젝트 규모(1인 유지보수, 트래커 9명 대상 개인 프로젝트)에 비해
계층이 과했다.

**결정.** 최상위는 계층(`app`/`domain`/`infrastructure`) 3개로 줄이고, 그 아래에 기능
단위 패키지, 다시 그 아래에 계층 서브패키지를 둔다:

```
com.fconline
├── app/<feature>/{controller, facade, dto}      # HTTP 진입점 + 유스케이스 오케스트레이션
├── domain/<feature>/{service, repository, vo}   # 애그리게잇(루트는 패키지 루트)/규칙/포트
└── infrastructure/                              # JPA/QueryDSL 구현체, 외부 API 클라이언트
```

애그리게잇 루트(`Match`, `TrackedUser`, `Season` 등)는 feature 패키지 루트에 그대로 두고,
`service`/`repository`/`vo`만 서브패키지로 분리. 단순 CRUD만 필요한 애그리게잇은 리포지토리
포트/구현체를 분리하지 않고 Spring Data JPA 인터페이스를 `domain/<feature>/repository/`에
직접 둔다 — 포트/어댑터 분리는 실제로 구현체를 바꿀 계획이 있는 리포지토리에만 적용.
`app.sync`처럼 컨트롤러가 없는 기능(배치)은 `runner/MatchSyncCliRunner.java` 같은 CLI
진입점을 둔다.

**결과.** *좋아진 점*: 기능 하나를 보려면 `app/<feature>`, `domain/<feature>`만 보면 되고,
단순 CRUD 애그리게잇에 불필요한 포트 추상화를 강제하지 않아 보일러플레이트가 적다.
*트레이드오프*: "포트/어댑터를 언제 분리할지"가 명문화된 규칙이 아니라 매번 판단해야
한다. 여러 명이 동시에 작업하게 되면 계층 재세분화가 다시 필요할 수 있다.

**검토했던 대안.** 멀티 모듈 Gradle(규모 대비 과함), 헥사고날의 엄격한 포트 강제(전부
적용은 보일러플레이트만 늘림) — 둘 다 기각.

## 2. v1과 Supabase 프로젝트를 공유하되 전용 스키마로 격리

- **Status**: Accepted (2026-08-22, 스키마명은 같은 날 `v2`→`fconline`으로 재변경) · **관련 커밋**: `a8b90f1`, `7014154`

**배경.** v1(choiyonghan/fconline)이 지금도 GitHub Actions cron으로 쓰는 라이브 Supabase
Postgres 프로젝트를 v2도 재사용하기로 했다(새 DB를 새로 파지 않음). JDBC로 직접 붙어
Flyway 마이그레이션을 검증하다가, 같은 DB의 `public` 스키마에 v1의 `matches`/
`match_details`가 이미 있어 마이그레이션이 충돌하는 걸 발견했다.

**결정.** v1을 전혀 건드리지 않도록 v2 전용 Postgres 스키마로 완전히 격리한다(datasource
URL의 `currentSchema`, `flyway.schemas`/`default-schema`, `hibernate.default_schema`
전부 통일). 스키마명은 `v2`로 시작했으나, 개발 초반 발견한 매핑 버그(`goalsAgainst`가
자기 자신 값 저장, `save` 항상 0)로 저장된 데이터를 소급 반영하는 대신 **스키마명을
`fconline`으로 바꿔 완전히 새로 시작**했다. 마이그레이션 파일은 스키마를 하드코딩하지
않아 그대로 재사용, Flyway가 새 스키마를 만들어 같은 순서로 재생한다.

**결과.** *좋아진 점*: 새 Supabase 프로젝트 없이 기존 인프라 재사용, v1 운영에 전혀
영향 없음, "데이터가 이미 틀렸으면 마이그레이션으로 땜질 말고 스키마를 새로 판다"는
선례. *트레이드오프*: 스키마 전환은 코드만으로 안 된다 — `SUPABASE_JDBC_URL`의
`?currentSchema=...`를 GitHub Actions secret과 Render 환경변수 양쪽에서 직접 바꿔야
한다(사람이 기억해야 하는 수동 단계). 같은 Postgres 인스턴스를 v1과 계속 공유한다는
결합도 남음.

**검토했던 대안.** 완전히 새 Supabase 프로젝트 — 접속 정보(`SUPABASE_DB_PASSWORD`)를
v1에서 못 찾아 새로 발급해야 하는 번거로움이 있었지만 격리 수준은 더 높았을 것.
운영 비용/설정 단순성을 택해 스키마 격리로 결정.

## 3. Nexon 원본 페이로드를 jsonb로 병행 보존

- **Status**: Accepted (2026-08-22) · **관련 커밋**: `4af945d`, `04c2a7d`

**배경.** 전체 Nexon match-detail 스키마 대비 실제 저장 필드를 감사해보니 매치/선수
레벨 필드 절반가량(`division`, `matchEndType`, 개인 `spRating`/카드, 세부 패스·드리블·
공중볼 스탯 등 20~30개)이 파싱 코드에 없어 조용히 버려지고 있었다. 이미 `goalsAgainst`/
`save` 매핑 버그를 겪은 전례가 있어, 정규화 컬럼만 믿으면 같은 종류의 버그를 재동기화
전까지는 데이터로조차 확인 못 하는 상황이 반복된다는 우려가 있었다.

**결정.** v1이 이미 쓰던 방식(`shoot_detail`/`player_squad` jsonb 컬럼)을 그대로 채택 —
정규화 테이블 + 원본 jsonb 백업의 하이브리드로 간다. `match_details`에 jsonb 컬럼 추가,
이후 참가자 원본 전체(`raw_participant`)까지 확장 보존. `shoot_events`/`squad_entries`
(정규화 테이블)는 그대로 유지해 기존 집계 쿼리 성능에 영향 없음.

**결과.** *좋아진 점*: 아직 매핑 안 한/향후 API에 추가되는 필드도 재동기화 없이 DB
안에서 바로 꺼내 쓸 수 있고, 매핑 버그가 또 나와도 원본에서 즉시 백필 가능(Nexon API
재호출 불필요, 레이트리밋 절약). *트레이드오프*: 매치당 저장 용량 증가, 정규화 컬럼과
jsonb 원본이 어긋나는 상황에서 "어느 쪽이 진실인지" 헷갈릴 여지(jsonb가 원천, 정규화
컬럼은 파생값이라는 우선순위를 이 문서로 명시).

**검토했던 대안.** 모든 필드 컬럼화(API 변경마다 마이그레이션 필요, 낭비) / 원본 미보존
(초기 실제 상태, 매핑 버그 발견을 어렵게 만든 원인) — 둘 다 기각.

## 4. GitHub 저장소를 읽기 전용 캐시로 사용(스냅샷 배치)

- **Status**: Accepted (2026-08-23, 2026-08-25에 두 번째 사례로 재확인) · **관련 커밋**: `ac0fd55`, `8e70a5c`

**배경.** 두 화면이 "매번 여러 API를 조합해 무거운 데이터를 만들어야" 하는 문제를
겪었다: (1) `POST /api/v1/insights/ask`가 질문마다 종합 전적/기여도/어시스트 체인/
최근 경기/상대별 전적을 전부 재조회, (2) 메인 대시보드가 진입 시 백엔드(Render 무료
티어)를 실시간 호출해 백엔드가 잠들어 있으면 첫 로딩이 수십 초.

**결정.** 새 DB 테이블 대신 **GitHub 저장소 자체를 캐시 저장소로 쓴다**. 매일 아침
GitHub Actions 배치(`insight-snapshot.yml` KST 09:30, `dashboard-snapshot.yml` KST
09:45)가 데이터를 미리 조립해 `data/insight-snapshots/*.json`, `data/dashboard-
snapshot.json`으로 커밋하고, 백엔드/브라우저가 `raw.githubusercontent.com`에서 그대로
읽는다. 파일이 없거나 실패하면 즉석 조립으로 폴백. `render.yaml`의
`buildFilter.ignoredPaths: data/**`로 이 커밋은 백엔드 재배포를 유발하지 않는다.
대시보드는 한 걸음 더 나가 **백엔드를 아예 거치지 않고 브라우저가 직접**
`raw.githubusercontent.com`을 호출한다.

**결과.** *좋아진 점*: DB 테이블/마이그레이션 증가 없음, 대시보드는 백엔드가 콜드
상태여도 즉시 뜸, 같은 패턴을 두 번째 사용처에 그대로 재사용 가능(검증된 접근임을
방증). *트레이드오프*: 데이터가 최대 하루 지연돼 실시간성 필요한 화면엔 못 씀.
`raw.githubusercontent.com`이 `Content-Type: text/plain`만 내려줘서 RestClient
기본 JSON 컨버터로 바로 못 받고 `String`으로 받아 `ObjectMapper`로 직접 파싱하는
우회가 필요했다(이 우회가 없으면 이 경로가 항상 실패해 무거운 즉석 조립만 매번 탐 —
운영에서 실제로 겪음). 캡을 늘리면 커밋 파일 용량과 AI 프롬프트 토큰 비용이 같이 커짐.

**검토했던 대안.** DB에 스냅샷 테이블 추가(쓰기 경로 복잡도 증가, Render DB 부하 증가로
기각) / Redis에 저장(옵트인이라 항상 켜져 있다는 보장이 없고, 하루 단위 정적 데이터는
Git 커밋 이력 자체가 audit trail이 되는 이점이 더 큼).

## 5. 정적 사이트를 루트로, SvelteKit은 `/app`로 격하

- **Status**: Accepted (2026-08-23, 같은 날 저녁 단일 페이지로 재통합) · **관련 커밋**: `e67d6c5`(site-root를 루트로), `8e70a5c`(대시보드를 index.html로 분리 신설), `886529b`(그날 저녁, 분리했던 대시보드를 report.html 유저 칩 "전체"로 다시 통합)

**배경.** 초기 계획은 SvelteKit CSR(`apps/web`)이 유일한 프론트엔드였다. 별도로(Claude
Artifact로) 만들어 쓰던 매치 리포트 정적 페이지를 "라이브 백엔드를 직접 호출하는 정적
페이지"로 재작성했더니 SvelteKit 앱보다 훨씬 빠르게 기능이 늘었다 — 결과적으로 이
정적 페이지(`site-root/`)가 매치 상세 모달, 인터랙티브 슈팅 위치, xG 추이, AI 질문,
대시보드, MOM/Worst 등 SvelteKit 앱보다 훨씬 많은 기능을 갖추게 됐다.

**결정.** `site-root/`(순수 HTML/CSS/JS, 빌드 스텝 없음)를 사이트 루트(`/`)로 승격.
`apps/web`(SvelteKit)은 `/app` 서브패스로 격하 — 삭제하지 않고 계속 빌드/배포는 하지만,
신규 기능 개발은 전부 `site-root/`에서 이루어진다(사실상 동결). `deploy-web.yml`이 두
산출물을 하나의 `site/`로 조립.

`site-root/` 내부 구조는 같은 날 안에 한 번 더 바뀌었다 — 처음엔(`8e70a5c`)
`index.html`(9인 요약 대시보드) + `report.html`(개인별 리포트) 2페이지였지만, 몇 시간
뒤(`886529b`) **`report.html` 하나로 재통합**됐다: 유저 칩 맨 앞에 "전체" 칩을 추가해
누르면 개인 리포트 섹션을 숨기고 9인 요약을 그 자리에 보여주는 방식으로 바꾸고,
`index.html`은 `report.html`로 리다이렉트만 하는 빈 페이지로 남겼다. 즉 **현재
`report.html`(과 `report.js` 하나)이 유일한 실제 진입점**이고, "대시보드"는 별도 페이지가
아니라 그 안의 한 상태("전체" 칩 선택)다. 대시보드 기본 화면은 여전히 백엔드를 안 거친다
— 유저 칩 목록조차 `data/dashboard-snapshot.json`의 `ranking`에서 뽑고, 실제 유저 칩을
누르는 순간에만 라이브 API를 지연 로드한다.

**결과.** *좋아진 점*: 빌드 도구 없이 파일을 바로 고칠 수 있어 반복 속도가 빠름(1인
유지보수 특성상 이점이 큼), 전용 API 없는 집계도 클라이언트 세션 캐시로 즉석 계산해
붙이기 쉬움. *트레이드오프*: `site-root/`는 컴포넌트/타입 시스템/빌드 검증이 없어
리팩터링 안전망이 약함(`report.js`가 계속 커지는 중이고, 근사 xG 로직이 Java에도
중복 이식돼 수동 동기화가 필요 — [§11](#11-api에-없는-지표xgmom는-자체-데이터로-근사-산출)
참고). `apps/web`은 사실상 죽은 코드지만 여전히 빌드/배포되며 CI 시간과 저장소 복잡도만
차지 — 정리(완전 제거 또는 명시적 아카이브) 필요성이 아직 판단되지 않은 상태. 두
프론트가 API 클라이언트 로직을 각자 구현하지만, `apps/web`이 동결 상태라 실제로는
`site-root/`만 맞추면 됨.

**검토했던 대안.** SvelteKit으로 계속 개발(타입 안전성은 더 좋았겠지만 빌드 없이 바로
고치는 속도 이점을 택함) / `apps/web` 이 시점에 완전 삭제(정리 비용을 미루고 일단
살려둠 — 아직 미해결).

## 6. 백엔드 Render / 프론트 GitHub Pages 분리 배포 + 콜드스타트 대응

- **Status**: Accepted (2026-08-22) · **관련 커밋**: `afa1718`, `f3c737d`, `75f5921`

**배경.** GitHub Pages는 정적 파일만 서빙 — 프론트 배포 직후 "백엔드가 실행 중인지
확인해 주세요" 에러만 떴다. 상시 실행 백엔드가 필요했지만 유료 호스팅은 피하고 싶었다.

Render 대시보드에서 직접 입력. Render 무료 티어는 15분 미접속 시 슬립되므로, 별도

최근 커스텀 매치 10건씩 병렬 조회**로 확장 — 깨우기와 실사용 데이터 확보를 한 호출로
겸함.

**결과.** *좋아진 점*: 완전 무료로 상시 배포 유지, 프론트/백엔드 독립 배포로 한쪽
장애가 다른 쪽을 막지 않음, "빈 핑"에서 "실사용 데이터 겸용"으로 발전. *트레이드오프*:
Render 무료 티어 정책 변경 리스크(최근에도 "자동배포가 비정상적으로 느릴 때가 있다"는
이슈로 남아있음), 10분 핑 실패/비활성화 시 콜드스타트 재발(§4의 대시보드 스냅샷이
이 상황에서도 최소 화면은 뜨게 하는 안전망), 512MB 힙 제한으로 무거운 배치는 별도
GitHub Actions 러너에서 처리(§9).

**검토했던 대안.** 백엔드도 정적 호스팅(Spring Boot 앱 특성상 애초에 불가능) / 유료
호스팅(비용 부담 회피, 무료 티어 + 콜드스타트 우회 조합 택함).

## 7. AI 벤더: Gemini ↔ Groq 왕복, 모델 등급의 RPD/TPM 함정

- **Status**: Accepted (2026-08-31, Gemini로 최종 정착) · **관련 커밋**: `6030b66` → `4db42a7` → `85f7f70`/`32e5b06` → `9920e8e` → `27c1ab8`

**배경.** `insights/ask`(자연어 질문)와 대시보드 AI 랭킹은 무료 티어 LLM API가
필요했다. 이 선택을 하루 안에 **Gemini → Groq → Gemini**로 두 번 오갔다 — 각 단계의
실측 결과를 남겨, 다음에 또 "무료 티어가 부족하다"는 이유로 벤더를 바꾸기 전에 반드시
이 절부터 읽어야 한다.

**1단계 — Gemini(최초), 하루 20회 한도로 좌초.** 당시 키로 쓸 수 있는 모델이
`gemini-3.6-flash` 하나뿐이었고(`gemini-2.5-flash`는 404, `gemini-3-flash`는 존재하지
않는 ID), 무료 하루 한도 **RPD 20**으로 운영 중 실제 `RESOURCE_EXHAUSTED`를 겪었다.

**2단계 — Groq로 전환, TPM이 진짜 병목이었음을 뒤늦게 발견.** "하루 14,400회까지
무료"라는 정보만 보고 전환했지만, 진짜 병목은 하루 횟수(RPD)가 아니라 **분당 토큰
(TPM)**이었다. 이 프로젝트 인사이트 프롬프트는 성격 리포트를 통째로 넣어 질문 1건당
약 1만~2만 토큰인데: `llama-3.3-70b-versatile`는 이 키의 `/v1/models` 목록에 아예
없어 404, `openai/gpt-oss-120b`는 TPM 8,000 고정이라 질문 1건도 못 받고 413,
`groq/compound`(TPM 30,000, 내부적으로 `meta-llama/llama-4-scout-17b-16e-instruct`
사용)는 겉보기엔 여유 있었지만 **내부적으로 `openai/gpt-oss-120b`로도 라우팅될 때가
있어**(`usage_breakdown` 필드로 실측 확인) 큰 프롬프트가 우연히 그쪽으로 가면 여전히
413/429 — "모델 하나를 골랐다"고 안심할 수 없는 합성 모델이었다.

**3단계 — Gemini로 복귀, "모델 등급마다 다르다"는 걸 놓쳤던 게 원인.** 새 구글 계정으로
키를 다시 발급해 `aistudio.google.com/rate-limit`(로그인 후 대시보드로만 확인 가능,
API로는 조회 불가)을 보니, **`gemini-3.6-flash`/`-pro` 등 일반 계열만 RPD 20으로
막혀있고, `gemini-3.1-flash-lite`/`gemini-3.5-flash-lite` 같은 `*-flash-lite` 계열은
신규 사용자에게도 RPD 500 · TPM 250,000이 열려 있었다**. "Gemini는 신규 사용자라
못 쓴다"는 최초 진단 자체가 모델 하나만 시도해보고 내린 성급한 결론이었다.

**결정.** 최종 벤더 **Gemini**, 모델 **`gemini-3.1-flash-lite`**(`GEMINI_MODEL`로
재정의 가능). `infrastructure/gemini`(`GeminiApiClient`/`GeminiApiProperties`) —
Generative Language API(v1beta, `generateContent`), 인증은 URL 쿼리스트링이 아니라
`x-goog-api-key` 헤더. `ask()`/`askJson()` 두 메서드(`askJson`은
`responseMimeType: application/json` 강제, 대시보드 AI 랭킹처럼 파싱 필요한
호출부용). 429/503은 시도마다 대기를 늘려가며 재시도(3초→6초, 최대 3회).

**결과.** *좋아진 점*: 실제 프롬프트 크기(성격 리포트 포함 약 1만 토큰) 그대로 curl로
재현 테스트해 정상 응답 확인(TPM 250,000 대비 여유 큼), RPD 500/일이면 트래커 9명이
나눠 써도 충분, 응답 품질도 양호. *트레이드오프*: "신규 사용자"/"무료 티어" 같은
뭉뚱그린 표현에 속으면 안 됨 — 같은 벤더 안에서도 모델 등급마다 RPD/TPM이 완전히
다르다(다음에 모델을 바꿀 땐 반드시 대시보드에서 실제 등급을 먼저 확인). API로는
RPD/TPM 조회가 안 돼 자동화된 사전 검증이 불가능 — 모델을 바꿀 때마다 사람이 수동
확인해야 함. 프롬프트 자체(성격 리포트 통째로 포함)가 여전히 큼 — 지금은 Gemini의
넉넉한 TPM 덕에 괜찮지만 리포트가 더 길어지거나 트래커가 늘면 다시 압박받을 수 있음.

**검토했던 대안.** 프롬프트 크기를 줄여 아무 벤더나 쓸 수 있게 하기(리포트 요약/캡핑은
사용자가 선호하는 리포트 품질을 해치는 트레이드오프라 보류) / OpenRouter 무료 모델
(Gemini flash-lite 실측이 이미 충분히 좋아 추가 검증 없이 보류).

## 8. Redis(Upstash) 캐시는 옵트인 + fail-open

- **Status**: Accepted (2026-08-30) · **관련 커밋**: `a6f9371`, `d46a64e`/`0d1b4fb`/`9956ed7`, `16d205b`, `96b6981`

**배경.** `RecordFacade`/`InsightFacade`의 조회 API가 매 요청마다 DB를 다시 쳤고,
`InsightFacade.ask()`는 §7 벤더가 뭐든 무료 티어 호출 한도가 있어 같은 질문 반복
호출을 줄이는 게 의미가 있었다.

**결정.** `spring.cache.type`을 `CACHE_TYPE` 환경변수로 제어(기본값 `simple`=인메모리).
**`REDIS_URL`/`CACHE_TYPE` 둘 다 채워야 실제로 Redis를 쓴다** — 로컬/CI/테스트는 항상
인메모리. `management.health.redis.enabled=false` — 캐시는 있으면 좋고 없어도 그만인
최적화, 앱 가용성의 전제조건이 아니다(Redis 장애가 Render 헬스체크를 DOWN으로 끌고
가면 안 됨). `LoggingCacheErrorHandler`로 캐시 조회/저장/삭제 실패를 예외로 전파하지
않고 로그만 남긴 뒤 원본 조회로 폴백(fail-open). 캐시 값 직렬화는 앱의 `ObjectMapper`를
복사해 폴리모픽 타입 정보(`@class`)를 켠 버전을 씀 — 타입 정보 없이 저장했다가
역직렬화 실패하던 버그, record 타입별 캐시 미분리 버그, `Page` 인터페이스라 특히
깨지기 쉬워 캐시 대상에서 뺐다가 `CachedPage` 래퍼로 다시 포함시킨 시행착오가 전부 이
결정 과정에서 나왔다. 모든 캐시 TTL을 **3시간으로 통일**(요청) — 캐시별 세분화 실익이
크지 않다고 판단.

**결과.** *좋아진 점*: Redis 없어도(로컬/CI) 완전 정상 동작, Redis 장애가 서비스 전체
장애로 안 번짐, 대시보드 배경 웨이크업 같은 반복 호출 패턴에서 DB/AI 호출을 실질적으로
줄임. *트레이드오프*: 폴리모픽 직렬화는 편하지만 저장된 클래스가 리팩터링(패키지
이동/이름 변경)되면 기존 캐시 값이 역직렬화 실패할 수 있다 — TTL 3시간이라 최악의
경우도 3시간 내 자연 소멸되지만, **배포 직후 코드는 고쳤는데 캐시에 남은 옛 값이 계속
나오는 상황**이 실제로 재현됐다(성격 리포트 charset 버그 수정 후에도 캐시가 살아있어
깨진 값이 한동안 계속 나옴). 코드를 고쳐도 **캐시는 별도로 무효화해야 할 수 있다**는
걸 기억할 것 — 현재는 Upstash 콘솔에서 키를 수동으로 지우거나 TTL 만료를 기다리는 것
외엔 방법이 없다(actuator 캐시 엔드포인트 미노출). 캐시 이름이 늘어날수록
`RedisCacheConfig`의 타입 매핑 테이블도 같이 늘어나야 하고, 등록을 빠뜨리면 조용히
기본 직렬화로 빠져 역직렬화 실패가 재발할 수 있다.

**검토했던 대안.** 캐시 없이 매번 DB 조회(대시보드 배경 웨이크업처럼 병렬 호출이
몰리는 패턴에서 체감 지연) / 애플리케이션 인메모리 캐시만 사용(Render 인스턴스 재시작
때마다 초기화돼 배포마다 콜드 상태가 되는 게 아쉬워 외부 캐시를 옵트인으로 추가).

## 9. 배치는 인앱 스케줄러 대신 GitHub Actions cron

- **Status**: Accepted (2026-08-22부터 누적 확립) · **관련 커밋**: `cde4590`(sync 배치), `ac0fd55`(insight-snapshot), `8e70a5c`(dashboard-snapshot), `f3c737d`(헬스체크 핑)

**배경.** 매치 동기화, 인사이트 스냅샷, 대시보드 스냅샷, 콜드스타트 방지 핑까지 —
전부 "정해진 시각에 한 번 실행하고 끝나는" 작업이다. 백엔드는 Render 무료 티어
512MB([§6](#6-백엔드-render--프론트-github-pages-분리-배포--콜드스타트-대응))라 상시
떠 있는 인스턴스 안에서 스케줄러(예: `@Scheduled`)로 무거운 동기화까지 돌리면 메모리
여유가 부족하고, 무료 티어가 슬립될 때 스케줄이 밀리는 문제도 있다.

**결정.** 배치는 전부 **GitHub Actions cron**으로 분리한다 — 앱 프로세스와 완전히
독립된 별도 러너에서 실행:

- `sync.yml`: 6시간마다(KST 03/09/15/21시 15분) CUSTOM/OFFICIAL 매치 동기화.
- `insight-snapshot.yml`: 매일 KST 09:30, AI 질문용 스냅샷.
- `dashboard-snapshot.yml`: 매일 KST 09:45(sync·insight-snapshot 다음 순서), 대시보드
  요약 + AI 랭킹.
- 콜드스타트 방지 핑: 10분마다 `/actuator/health`.

각 배치는 `--spring.profiles.active=<profile>`로 지정된 전용 Spring 프로파일 +
CLI 러너(`*CliRunner`)로 실행되고, DB 접속 정보는 GitHub Actions repo secret으로
주입한다. 배치 결과가 파일(스냅샷 JSON)이면 워크플로우의 "Commit and push" 스텝이
git에 반영한다.

**결과.** *좋아진 점*: 백엔드 인스턴스 메모리를 배치가 잠식하지 않음, 배치 실행이
백엔드 가동 여부와 무관(백엔드가 슬립 중이어도 배치는 정상 실행), 각 배치를
`workflow_dispatch`로 수동 트리거 가능해 디버깅이 쉬움, GitHub Actions 무료 티어
한도 내에서 충분히 운용 가능. *트레이드오프*: 배치마다 매번 `./gradlew :backend:bootJar`로
전체 빌드를 다시 하므로(빌드 캐시가 있어도) 실행 시간이 필요 이상 걸릴 수 있음.
여러 워크플로우가 같은 시크릿(`SUPABASE_*`, `GEMINI_API_KEY` 등)에 의존하므로,
시크릿을 하나 빠뜨리면 그 배치만 조용히 실패(대부분 폴백이 있어 워크플로우 자체는
안 죽지만 — 예: AI 랭킹 실패 시 승률순 대체 랭킹). 크론 스케줄이 서로 순서에 의존하는
경우(sync → insight-snapshot → dashboard-snapshot)가 있는데, 이 순서는 크론 시각
간격으로만 보장돼 있어 앞 배치가 예상보다 오래 걸리면 뒤 배치가 옛 데이터를 볼 수
있다.

**검토했던 대안.** 앱 내 `@Scheduled`(Render 무료 티어 메모리/슬립 제약과 상충해 기각) /
별도 서버리스 함수(AWS Lambda 등, 추가 인프라·비용 없이 이미 쓰는 GitHub Actions로
충분해 불필요).

## 10. 성격 리포트: Supabase Storage + ouid 키

- **Status**: Accepted (2026-08-31) · **관련 커밋**: `b51b70f`(도입), `5468fdc`(키를 실명→ouid로 변경), `27c1ab8`(charset 버그 수정)

**배경.** `insights/ask`가 전적 데이터뿐 아니라 이 사람의 성격/말투/성향까지 참고해
더 캐릭터에 맞는 답변을 하도록, Claude Code가 카톡 대화 원본을 직접 읽고 손으로 써둔
친구 성격 리포트(`.md`)를 붙이기로 했다. 저장소는 이미 DB로 쓰고 있는 Supabase의
Storage(오브젝트 스토리지) 기능을 재사용 — 새 인프라를 늘리지 않음. 파일 키를 처음엔
실명(한글)으로 썼다가, Supabase Storage 서버가 키에 비-ASCII 문자가 들어오면 URL
인코딩을 제대로 해도 "InvalidKey" 400으로 거절하는 걸 운영에서 겪었다.

**결정.** private bucket에 **ouid를 파일 키**로 저장(예: `c4f8613f...md`) — 이미
`insight-snapshots`(`{ouid}_{matchType}.json`)에서 쓰는 것과 같은 키 관례. 계정을
2개 쓰는 사람(예: 욱냥0I + 지린성에사는욱구)은 ouid마다 같은 리포트를 각각 올려야
한다. 조회는 `PersonalityReportClient`가 서비스 롤 키로 인증해 RLS를 우회(백엔드
전용, 브라우저엔 절대 노출 안 됨). 응답은 Redis에 TTL 3시간 캐싱
([§8](#8-redisupstash-캐시는-옵트인--fail-open)). 응답 바이트는 Content-Type의
charset 유무와 무관하게 **항상 UTF-8로 직접 디코딩**한다 —
`.body(String.class)`(Spring `StringHttpMessageConverter`)를 쓰면 Content-Type에
charset이 없을 때 기본값 ISO-8859-1로 디코딩돼 한글이 깨지는 버그를 실사용 중
발견해 `.body(byte[].class)` + `new String(bytes, UTF_8)`로 수정했다.

**결과.** *좋아진 점*: 새 인프라 없이 기존 Supabase 프로젝트 재사용, ouid 키로
InvalidKey 문제 해결, UTF-8 강제 디코딩으로 charset 관련 인코딩 버그 원천 차단.
*트레이드오프*: 리포트가 없는 유저(빈 Optional)는 캐싱하지 않는다는 예외 처리가 필요
(캐시가 null 값 저장을 막아 IllegalArgumentException이 쌓이는 걸 피하려고). 리포트를
새로 올리거나 고쳐도 최대 3시간은 캐시가 이전 값을 돌려준다 — 급하게 반영해야 하면
수동 캐시 무효화가 필요(§8과 동일한 한계). 이 프로젝트가 public 저장소라 리포트
콘텐츠(사람 이름/카톡 대화 기반) 자체는 git에 올리지 않고 반드시 private bucket에만
둬야 한다는 운영 규율에 의존한다(코드로 강제되지 않음).

**검토했던 대안.** 리포트를 DB 컬럼/테이블로 저장(오브젝트 스토리지가 이미 있고 파일
단위 관리가 더 자연스러워 기각) / 파일 키로 실명 사용(InvalidKey 400으로 이미 실패,
ouid로 교체).

## 11. API에 없는 지표(xG·MOM)는 자체 데이터로 근사 산출

- **Status**: Accepted (2026-08-25부터 반복 개선, 2026-08-31 JS/Java 드리프트 수정) · **관련 커밋**: `7c28875`(MOM/Worst 도입), `5c805a2`(결정력 공식), `cb4ee3e`(xG를 구역 기반에서 거리·각도 로지스틱 회귀로 전면 교체 — 초기 구역 기반 버전(`d7ad531` 등)은 이 커밋으로 대체돼 더는 존재하지 않음)

**배경.** Nexon 공식 API에는 xG(기대 득점)도, MOM(Man of the Match) 플래그도 없다
(`grep` 결과 `mom`/`spRating` 외 관련 필드 없음을 확인). 그렇다고 이 지표들을 아예
포기하면 매치 리포트의 분석 깊이가 크게 떨어진다.

**결정.** 둘 다 **자체 데이터 기반 근사치**로 계산한다:

- **xG**: 공식 xG 모델이 아니라, 정규화 좌표(x,y)를 실제 피치(105×68m)로 환산해 골대까지
  거리와 시야각(코사인 법칙)을 구하고 `logit = 0.5 − 0.15×거리 + 0.05×각도`를 시그모이드에
  넣는 로지스틱 회귀 근사식. 여기에 **슛 유형별 난이도 배율**(헤더 0.70배, 발리 0.82배,
  바이시클킥 0.55배, 플레어샷/무회전 0.85배, 프리킥 0.80배, PK 1.15배, 나머지는 1.0)을
  곱해 [0,1]로 캡하고 소숫점 둘째 자리로 반올림한다. (초기엔 전 유저 슈팅 표본을 구역(zone)
  으로 나눠 구역별 실제 전환율을 쓰는 경험적 방식이었으나, `cb4ee3e`에서 표본 수집이 필요
  없는 순수 함수로 전면 교체됐다 — 대시보드 진입 시 표본을 미리 모을 필요가 없어져 지연
  로드 코드도 함께 정리됨.) 이 계산은 `report.js`(브라우저, `calcXg`)와
  `ExpectedGoalsCalculator`(Java, `domain/match/vo`) **양쪽에 각각 구현**돼 있다 — 배치가
  브라우저가 아니라 Java 프로세스라 JS를 그대로 재사용할 수 없었기 때문. 결정력 지표는
  "실제 득점 − xG" 차이로 계산(초기엔 비율(%)이었다가 변경).
- **xA(기대 어시스트)**: 2026-08-31 추가. 새 모델을 만들지 않고 **xG를 그대로 재사용** —
  `shoot_events`가 골 여부와 무관하게 슛마다 `assist`/`assist_sp_id`를 갖고 있다는 걸
  확인했고(Nexon 원본 `shootDetail[]`을 그대로 파싱, 실제 라이브 매치 데이터로 "노골인데
  어시스트는 있는" 슛이 다수 존재함을 검증), 그 슛의 xG(슈터 위치·유형 기준으로 계산한
  값)를 슈터가 아니라 어시스트 제공자(`assistSpId`)에게 귀속시키는 방식으로 계산한다.
  `RecordFacade.xaBySpId`가 "전체 선수 스탯"의 xA 열을 채운다. 대시보드/AI 랭킹 레벨
  ("팀 전체 xA")로 확장할지는 별도로 결정 예정 — 지금은 개인별 표에만 반영.
- **MOM/Worst Player**: API에 플래그가 없으므로 **선수 평점(rating) 비교**로 대체 —
  경기 내 평점 최댓값=MOM, 최솟값=Worst(0평점은 제외). 한줄평은 그 선수의 두드러진
  스탯 우선순위(골 > 어시스트 > 세이브 > 태클+인터셉트 > 평점만)로 자동 생성.

**결과.** *좋아진 점*: 공식 API에 없는 지표도 매치 리포트/대시보드에서 일관되게 보여줄
수 있음, 구역 기반→순수 함수 전환으로 표본 수집/캐싱 코드 전체가 사라져 오히려 더
단순해짐(항상 즉시 계산, "계산 중…" 상태 없음). *트레이드오프*: **공식 xG가 아니므로
다른 사이트/방송의 xG 수치와 다를 수 있다** — 이 프로젝트 안에서만 일관된 상대적
지표로 봐야 함(문서화 필요, 사용자에게 오해를 줄 수 있는 지점). **JS/Java 두 구현을
수동으로 동기화해야 한다** — 이 경고가 실제로 현실이 됐다: `cb4ee3e`가 슛 유형별
난이도 배율을 `report.js`(`calcXg`)에만 추가하고 Java `ExpectedGoalsCalculator`엔
포팅하지 않아, "전체 선수 스탯"의 xG/결정력 열과 대시보드 요약(AI 랭킹 프롬프트에도
들어감)이 헤더·바이시클킥 골이 많은 선수의 xG를 과대평가하는 드리프트가 며칠간
남아있었다(2026-08-31 발견 즉시 수정 — `PlayerShotPoint`/`ShotPointResponse`에 이미
있던 `shootType`을 `calcXg` 호출부 2곳에 마저 연결). 코드 주석("반드시 같은 공식이어야
한다")만으로는 이런 드리프트를 막지 못한다는 게 실증된 셈 — 재발 방지로
`ExpectedGoalsCalculatorTest`(golden test)를 추가했다: report.js의 `calcXg`를 Node로
직접 실행해 뽑은 좌표/슛유형/xG 조합 8건을 하드코딩해두고 Java 쪽이 같은 값을 내는지
검증한다. **자동 동기화는 여전히 안 된다** — `report.js`의 공식(상수·배율)을 고치면
이 테스트의 기대값도 같은 방법으로 다시 뽑아 수동으로 갱신해야 하지만, 최소한 "한쪽만
고치고 잊어버리는" 상황은 이 테스트가 실패로 잡아준다. MOM/Worst는 "그 경기에서 잘한
선수"의 근사치일 뿐, 실제 게임 내 판정(있었다면)과 다를 수 있다.

**검토했던 대안.** xG를 아예 표시하지 않음(분석 깊이 저하로 기각) / MOM을 매치 종료
직후 최고 평점 1명으로만 단순 표기(더 풍부한 한줄평 생성을 위해 스탯 우선순위 로직
추가) / xG 계산을 백엔드 전용 API로 통합해 프론트가 그 결과만 쓰기(현재 미채택 — JS
쪽이 클라이언트 세션 캐시로 즉석 계산하는 이점이 있어 이중 구현 상태 유지 중, 향후
정리 후보).
